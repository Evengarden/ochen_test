# Архитектура Vector Composer

Плагин состоит из интерфейса `ui.html`, чистой логики в `src/engine.ts`, AI-адаптеров в `src/llm.ts` и слоя Figma API в `src/plugin.ts`. TypeScript компилируется в `code.js`; отдельного backend нет. UI и runtime обмениваются сообщениями через `postMessage` и `figma.ui.onmessage`.

## Хранение элементов

Базовый каталог в `src/catalog.ts` содержит 10 смысловых объектов и 40 исходных вариантов: две детализации `L/S` × две роли `main/background`. Метаданные связывают semantic ID, название, теги, синонимы, Figma node ID и габариты. `L/S` — разные исходные рисунки по детализации, а не простое масштабирование одного рисунка.

Файлы `assets/svg/L|S/main|background/*.svg` хранят векторные исходники для документов без исходных Figma-узлов. `assets/manifest.json` содержит реестр, `assets/palettes.json` — базовые палитры.

Импортированные элементы находятся на странице `Vector Composer · Library`. Каталог пользовательских библиотек и связи с узлами сохраняются в документе через Plugin Data. При наличии plugin ID используется private Plugin Data, без него — shared namespace `vector_composer`. Профили AI и пользовательские палитры сохраняются отдельно в `figma.clientStorage`; API-ключ остаётся только в памяти сеанса.

## Извлечение и импорт

При сканировании плагин загружает страницы документа и ищет исходные узлы по ID и сохранённым связям. Источник должен поддерживать клонирование, масштабирование и экспорт и иметь корректные габариты. Если нативный источник базового варианта отсутствует, плагин создаёт его через `figma.createNodeFromSvg` из поставляемого SVG и сохраняет связь для повторного использования.

Пользовательские SVG поступают из File API интерфейса, проходят проверку допустимой структуры и импортируются тем же Figma API. Скрипты, растровые вставки и внешние ресурсы отклоняются. Выделенные Figma-узлы импортируются копиями. Варианты связываются по `semanticId / size / role`; повторный импорт заменяет соответствующий пользовательский вариант после успешного создания источника.

Офлайн-подготовка базовой библиотеки выполняется отдельно: `.fig` → бинарный `canvas.fig` → Kiwi-декодер → исходные vector paths → SVG. Инструменты находятся в `tools/`. Они сохраняют исходные команды контуров, но могут воспроизводить сложные эффекты иначе, чем нативный экспорт Figma.

## Выбор и повторное использование

1. LLM получает запрос и список доступных semantic ID и ролей для выбранной библиотеки и детализации. Адаптер проверяет ответ по каталогу. Неизвестные ID и недоступные варианты отклоняются; при ошибке провайдера композиция не создаётся.
2. `engine.ts` рассчитывает позиции, повороты и порядок объектов по габаритам, формату, шаблону и seed. Для всей сцены используется единый масштаб. LLM не создаёт геометрию и не управляет координатами.
3. Runtime вызывает `clone()` для выбранных источников и помещает копии во фрейм на странице `Vector Composer · Outputs`. В метаданных копий сохраняются источник, semantic ID, детализация, роль и масштаб. Исходные контуры и исходные цвета библиотеки не меняются.
4. При смене роли используется клон соответствующего исходного варианта `main/background`. Детализация также выбирается из существующих вариантов.

Сцену можно редактировать нативными инструментами Figma: перемещать, вращать, дублировать, удалять объекты и менять порядок слоёв. После ручных изменений метаданные сцены автоматически не пересчитываются.

## Цвет и SVG-экспорт

Перекраска работает по сохранённым исходным заливкам и обводкам копий. Базовые цвета сопоставляются со слотами палитры; для пользовательских SVG задаётся `sourceColorMapping`. Фоновые варианты получают только фоновые цвета, главные — фоновые или объектные. Несопоставленные пользовательские цвета сохраняются с предупреждением. Исходные цвета копий можно восстановить.

Готовый фрейм экспортируется через `exportAsync({format: 'SVG_STRING'})`; UI скачивает результат. Исходную библиотеку можно экспортировать отдельно в SVG и упаковать в ZIP в интерфейсе. PNG служат только превью и не подменяют векторные элементы композиции.

## Границы проверки

Node.js-тесты используют mock Figma API и HTTP; они проверяют логику, адаптеры и обработку ошибок. Python-проверки анализируют офлайн-ассеты. Эти проверки не подтверждают работу в редакторе: импорт manifest, доступ к провайдерам, создание сцены и нативный экспорт требуют ручного запуска в Figma Desktop. Инструкция запуска и сценарий демонстрации приведены в [README](README.md).
